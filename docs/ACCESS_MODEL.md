# Модель доступа MedHub

> Change note от 2026-03-16. Приоритетное уточнение к исходному ТЗ.

## Принцип

Все авторизованные пользователи имеют **одинаковый доступ** ко всем разделам, данным и действиям.

## Роли

В таблице `profiles` хранится поле `role` со значениями `patient` или `guardian`.

Роль — это **только атрибут профиля** (для отображения в UI). Роль **не влияет** на:
- доступ к разделам (dashboard, diary, documents, medications, profile);
- возможность создавать, читать, редактировать или удалять данные;
- middleware, server actions или SQL-политики;
- любую бизнес-логику.

## Data Ownership

Медицинские данные принадлежат **пациенту** (`patients` table), не auth user.
Все продуктовые таблицы ссылаются на `patient_id`, не на `user_id`.
Несколько auth users привязаны к одному пациенту через `profiles.patient_id`.

Опциональное поле `created_by` в продуктовых таблицах — только для аудита (кто создал запись), не для access control.

## Что проверяется при доступе

Единственная проверка — **факт авторизации** + **привязка к пациенту**:
- middleware: есть ли валидная сессия Supabase;
- dashboard layout: `supabase.auth.getUser()` → redirect на `/login` если нет пользователя; проверка наличия `patient_id` в профиле;
- RLS-политики: через `profiles.patient_id` — user видит данные пациента, к которому привязан.

## Что НЕ реализуется

- Permission matrix по ролям
- Role-based guards в middleware, layout или server actions
- Разные наборы функций для patient и guardian
- Ограничение доступа к отдельным модулям по роли

## Обоснование

На текущем этапе MedHub — закрытое приложение для двух конкретных пользователей (пациент и опекун), работающих с одной общей базой данных пациента. Разграничение прав между ними не несёт ценности и добавляет ненужную сложность.
